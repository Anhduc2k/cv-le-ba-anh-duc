Dashboard — the platform app current focus

Ground-up rebuild of the customer dashboard, replacing an ageing Angular / Nx application: landing pages, e-commerce, CRM and sales pipeline, tasks, marketing automation, reports, blog and workspace settings.

  • App structure — Next.js 16 App Router, React 19, TypeScript strict, Tailwind v4. Organised as three parallel route-group shells (dashboard, auth, full-screen builder) so builder and presenter views escape the dashboard chrome without duplicating routes; state is lifted to context only where it spans routes, and components are split by domain over a shared primitive layer.
  • API layer — one typed client fanning out to six separate backend products, split into per-domain modules. Each product requires a different identity header set (store-id, team-id, Owner-Id) and rejects the others at CORS preflight, and each keys off its own store id in a separate ID space — the wrong one returns an empty list rather than an error, so ids resolve once at bootstrap and are cached.
  • Data tables, the contract every list screen follows — server-side pagination, search debounced at 300 ms, sorting, filters, URL-synced state so reload and browser-back survive, and AbortController signals so rapid filter changes cannot race. Replaced client-side filtering that silently broke past page one.
  • CRM sales pipeline — Kanban for deals and tasks on @dnd-kit with list, to-do and forecast views over the same data. Card mutations are optimistic with snapshot rollback: the previous values are captured, the UI patches instantly, and the snapshot is re-applied if the write fails. Board totals come from server-computed summaries, never summed from the loaded page — the shortcut that silently reports wrong numbers once a pipeline exceeds one page.
  • Lead routing and segmentation — auto-assign rules as an ordered list reorderable by drag (priority re-indexed on drop), each holding a nested condition group, with ratio-weighted distribution across staff rather than plain round-robin. The segment builder nests condition groups under and/or glue, deriving both the available operators and the value-input type from the field: built-in fields route by field reference, custom fields by declared data type.
  • Custom report dashboards — assembled from a library of saved reports, widgets drag-reorderable and width-togglable on a responsive grid. A parameter-mapping layer lets one dashboard control drive charts built on entirely different report schemas.
  • HTML → LadiPage converter — ingests an uploaded file or archive and turns a third-party page into an editable document. Conversion runs long server-side, so the client polls with staged backoff (tight for the first half-minute where most jobs finish, then slower) instead of holding a request open until the browser drops it; the size cap is enforced client-side too, so oversized files fail before the upload rather than after. The post-convert risk report uses the backend's own analysis, and derives the likely-diverging parts from the converted output when the backend runs in a mode that produces none.
  • Embedded micro-frontend — a separate flow-editor application mounted in an iframe with origin-validated postMessage both ways, so refreshed credentials can be pushed in after a token renewal, and the frame stays mounted across navigation so switching pages never reloads the editor mid-edit.

Identity & SSO LadiUID
  • Hold the JWT in a cookie rather than localStorage, deliberately: the edge middleware, the React app and the embedded legacy AngularJS builder then all read one value, so the legacy builder needs no token bridge and signing out in one tab propagates everywhere. Scoped SameSite=Lax, Secure over HTTPS.
  • Built the full identity surface against the platform's LadiUID service: sign-in, signup with OTP verification, password reset and change, session activity history, sign-out-all-devices.
  • OAuth2 with Google and Facebook through a popup bridge — a static relay page forwards the provider's ?code= to the opener via postMessage. The middleware whitelists that path, since the ordinary "authenticated user on an auth route → redirect" guard would otherwise hijack the callback and break every integration connect.
  • Two-factor authentication — TOTP enrolment, enable / disable, and a trusted-device list with per-device revocation.
  • Token-renewal interceptor — a 401 / 498 / 503 triggers one silent renewal and a single retry, with an opt-out flag so the auth endpoints themselves cannot recurse through it.
