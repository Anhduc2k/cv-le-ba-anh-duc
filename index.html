Builder — the editor customers author in

Drag-and-drop editor for landing pages, popups and slide decks, plus the checkout customers actually sell through. I own core editing surfaces on the production engine and built the canvas for its React successor.

Each plugin declares its own property schema, so a new element type ships without touching the canvas core.
  • Form & checkout — form builder with typed fields, required-field validation, reCAPTCHA (standard and enterprise), Vietnamese province / district / ward address pickers, cart, product and quantity selectors, coupons and order bumps. Checkout wires up to COD, bank transfer, VNPAY, MoMo, ZaloPay, ShopeePay, NAPAS, Stripe and PayPal.
  • Custom code — per-element and per-page HTML / CSS / JavaScript blocks edited in an embedded code editor, with SASS compiled in the browser, so power users extend a page without leaving the builder.
  • Engine architecture — a prototype-based LadiPageV2 class of roughly 460 methods partitioned across modules by concern: builder operations, getters, setters, mouse and keyboard events, HTML generation, snapping, rollback, attribute mapping, validation and responsive adaptation.
  • Undo/redo as diffed transactions, not state snapshots — opening a transaction captures the affected elements and their children, closing it diffs before against after and records only what actually changed as delete / update-old / update-new actions. History is capped and evicts oldest, and acting after an undo truncates the redo branch.
  • Snapping — grid snap plus element snap against neighbours' edges and centres, with live guide lines, group-level snapping and snap-on-resize.
  • Built the React canvas for the successor builder: the same snap-and-align model at a 5 px threshold, an undo history where every entry carries an action label and timestamp so the panel reads as a list of changes, and presenter mode over BroadcastChannel keeping the presenter and audience windows on the same slide, reveal step and timer.
  • Deliver custom-coded landing pages for enterprise clients on the builder's extension model rather than forking it.

  • Production dashboard — React 18 in an Nx monorepo, with Redux + redux-thunk for global state, React Router 5, and REST over axios; i18next for translations and Socket.IO for live updates.
  • Rewrite — Next.js 16 App Router, React 19, TypeScript strict, Tailwind v4. Deliberately dropped Redux: server state lives in the data layer, cross-route state in a small set of React contexts, and everything else stays local to the feature — which removed the boilerplate layer without losing shared state.
  • App structure — three parallel route-group shells (dashboard, auth, full-screen builder) so builder and presenter views escape the dashboard chrome without duplicating routes; components split by domain over a shared primitive layer.

Each product requires a different identity header set (store-id, team-id, Owner-Id) and rejects the others at CORS preflight, and each keys off its own store id in a separate ID space — the wrong one returns an empty list rather than an error, so ids resolve once at bootstrap and are cached.
  • Data tables, the contract every list screen follows — server-side pagination, search debounced at 300 ms, sorting, filters, URL-synced state so reload and browser-back survive, and AbortController signals so rapid filter changes cannot race. Identity & SSO LadiUID
  • Hold the JWT in a cookie rather than localStorage, deliberately: the edge middleware, the React app and the embedded legacy AngularJS builder then all read one value, so the legacy builder needs no token bridge and signing out in one tab propagates everywhere. Scoped SameSite=Lax, Secure over HTTPS.
  • Built the full identity surface against the platform's LadiUID service: sign-in, signup with OTP verification, password reset and change, session activity history, sign-out-all-devices.
  • OAuth2 with Google and Facebook through a popup bridge — a static relay page forwards the provider's ?code= to the opener via postMessage. The middleware whitelists that path, since the ordinary "authenticated user on an auth route → redirect" guard would otherwise hijack the callback and break every integration connect.
  • Two-factor authentication — TOTP enrolment, enable / disable, and a trusted-device list with per-device revocation.
  • Token-renewal interceptor — a 401 / 498 / 503 triggers one silent renewal and a single retry, with an opt-out flag so the auth endpoints themselves cannot recurse through it.
